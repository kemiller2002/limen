For AI coding agents

Where the change goes.

Humans ask when architecture is unclear. Agents infer and continue. So this page states where things go rather than describing qualities to aim for — and the repository's AGENTS.md is the machine-readable version of it.

Contract

Ten rules, all MUST.

Violating one is a defect regardless of whether tests pass.

Before you change anything

Read the boundary first.

The architecture here is unusual, and code that looks reasonable by mainstream front-end conventions is often wrong. The single most useful file is the protocol — about eighty lines, and it is the architecture.

The boundary, in detail →

  1. 01
    Authoritative application state lives in the engine, nowhere else
  2. 02
    Do not introduce application state in JavaScript outside the engine
  3. 03
    Browser events enter only through data-event and the kernel
  4. 04
    Validation, legality and what-to-show are engine decisions
  5. 05
    Browser capabilities are reached only through an effect request
  6. 06
    HTML stays structural; CSS stays presentational
  7. 07
    The kernel stays generic — never branch on domain meaning in it
  8. 08
    All four HTTP outcomes are represented; OutcomeUnknown is not a failure
  9. 09
    Existing public contracts are preserved
  10. 10
    The repository's full check passes before you are done

Routing

The decision tree.

Most ambiguity resolves in the first three branches.

I need to add behavior.
│
├─ Is it purely visual (color, spacing, motion, hover)?
│  └─ YES → CSS. Stop. Do not route it through the engine.
│
├─ Is it document structure (an element, a label, a landmark)?
│  └─ YES → HTML. Add data-* only if the engine must drive it.
│
├─ Does it decide, validate, remember, or compute anything
│  about the application?
│  └─ YES → the engine. Add a state, a command, a transition,
│            and a projected key.
│
├─ Does it need HTTP or local storage?
│  └─ YES → the engine returns an EffectRequest. It does NOT
│            call fetch.
│
├─ Does it need a browser capability that does not exist yet
│  (clipboard, history, files, timers, focus)?
│  └─ YES → a protocol extension. A bigger change: propose it,
│            do not slip it in.
│
└─ Am I about to hold application state in JavaScript,
   outside the engine?
   └─ STOP. That is rule 1. Go back to the third branch.

The test that resolves most cases in one line: would the application behave differently because of this? Yes means the engine. No means HTML or CSS. “Which tab is showing” passes that test — it changes what is legal and what matters, so it is application state. “What color the active tab is” fails it, so it is CSS.

Checklist

Before and after.

Answer 1–8 before writing; confirm 9–13 before finishing.

Before

  1. What state changes? Which union member, in which state type?
  2. What event causes it, and from which element?
  3. Is the transition legal from every state it can be requested in? What happens when it is not?
  4. Is an external effect required, and of which kind?
  5. Who performs it? (The answer is: the kernel.)
  6. How does the result return, and how is a stale one rejected?
  7. Which projected keys change? Are capabilities projected explicitly?
  8. What HTML or CSS is needed? (Usually: none.)

After

  1. Am I creating duplicate state anywhere?
  2. Am I adding application logic outside the engine?
  3. Am I bypassing a boundary for convenience?
  4. What tests prove this — including the illegal case and the stale result?
  5. Does the full repository check pass?

This repository also enforces a work-item protocol in CI. Open one before editing, or the pull request is rejected regardless of whether the code is correct — see AGENTS.md.

If the documentation does not cover your case

Reason from the boundary, in order.

And if you conclude the architecture itself is the obstacle, say so explicitly and record it. Do not route around it silently — that is the one failure mode this design is least tolerant of.
