Evidence

What we have actually measured.

No quantitative claim about Limen is supported by evidence today. That sentence is the honest headline, and this page exists to keep it visible rather than let the benefits elsewhere on this site quietly harden into numbers nobody measured.

The benefits listed on the overview page are stated as architectural consequences — things that follow from where the boundary is drawn — not as outcomes anyone observed. “Application state exists in one place” is true because the engine is the only writer, not because a study found it.

Limen

What has been observed.

Two things. Both qualitative. Both from a real consumer project.

Observed · existence proof

An F# engine runs behind the boundary, unchanged

A separate Echelon Foundry project implements EngineTransport over the .NET WebAssembly runtime and drives a full F# engine through it, consuming this package directly. Its own source records that it required no kernel change.

Establishes: the claim that this interface is a sufficient seam for a WebAssembly engine is demonstrated, not merely argued. Does not establish: anything about performance, size, startup cost, or effort.

Observed · single incident

A silent failure found only by loading the page

In that same project, data-if was written on a <p> instead of a <template>. The kernel ignored it in silence, so an empty-state message never disappeared. No test in either project caught it.

Acted on: misplaced bindings now raise a reported binding error. Establishes one real usability defect — not a defect rate. It is one incident.

Adjacent, and not the same thing

SDE evidence is not Limen evidence.

Verified rather than assumed.

Echelon Foundry runs preregistered engineering trials of State-Directed Engineering, a construction method. Those trials produce genuinely useful numbers. They also do not use Limen — checked directly: both trial branches contain no reference to this package or any of its types, and declare zero runtime dependencies. They are Node command-line applications.

Attributing their results to Limen would be the single easiest mistake to make on a page like this, so it is called out rather than left to good intentions. The strongest result from those trials, stated as what it is:

An independent fresh-agent review produced 5 findings, 0 of which overlapped the builder's own 90-test suite and written self-review. Four were real defects.

That is evidence that heterogeneous verification finds what homogeneous verification misses. It is evidence about a method, on one run, with one reviewer, on one codebase — and it says nothing whatever about this architecture.

Discipline

What we refused to publish.

Usually the more informative list.

“Explicit state modelling reduces mistakes”

Tempting, adjacent, and contradicted by its own source. The originating project rates that hypothesis low confidence and records the contradiction itself: raw mistake counts came out roughly even. The defensible version is narrower — the effect appears to be in which mechanism catches a mistake, not in how many occur.

A speed comparison between two trials

One run took ~30 minutes, another ~3 hours 12 minutes. Reading “6× faster” out of that would be wrong: the second run also performed mutation testing, an independent verification phase, and a cross-experiment analysis. Different work, not different speed.

Token and cost figures

Almost all are marked unavailable — not exposed to agent in the source telemetry, explicitly rather than by omission. Exactly one sub-unit was ever instrumented. One measurement is not a rate, so it is not presented as one.

Two figures that do not reconcile

Identical test-line counts reported across two runs with different file counts, and a mistake tally whose breakdown sums to one more than its total. Both are recorded as open data-quality questions rather than published as measurements.

What would settle it

The trial that has not been run.

Nothing above isolates Limen, because no controlled comparison exists where Limen is the only variable. The blocker is instrumentation, not willingness: token, cost, and context figures are not exposed to a running agent in machine-readable form, and both existing trials record that and refuse to estimate.

Such a trial can measure time, files, defects and rework today. It cannot yet measure tokens or cost — which are the numbers most often asked for.
