Evidence

What the repository proves, and what it does not.

Limen now has stronger existence evidence than the old site showed: this website itself runs its application logic in F# WebAssembly behind the real kernel. That is useful. It is still not a controlled benchmark, and this page does not turn it into one.

Evidence discipline

Four categories, kept separate.

A structural property is not automatically a measured outcome.

L-1 · self-hosting

This site is now a real F# WebAssembly Limen application.

Mechanically verified existence proof.

F# owns application statesite/fsharp/Limen.Site.Engine/
.NET WebAssembly hosts itsite/fsharp/Limen.Site.Wasm/
Limen owns browser mechanicsBrowserKernel + explicit effects
TypeScript engine removedartifact check rejects site/app/engine.js

The F# engine drives release gating, evidence obligations, stale-result rejection, ambiguous deployment outcomes, reconciliation, the placement challenge, and the visible transition trace. TypeScript on the site side loads the runtime and transports serialized protocol messages; it does not contain those application concepts.

CI compiles and executes the F# engine tests, publishes the WebAssembly runtime into dist-site/wasm/, requires a real .wasm artifact, and fails if the legacy TypeScript application engine returns.

What this establishes: Limen's protocol and transport seam can host a real F# WebAssembly application with nontrivial state inside the Limen repository itself. What it does not establish: that this is faster, cheaper, smaller, easier, or less defective than another architecture.

L-2 · external consumer

The boundary also works outside its own showcase.

Observed existence proof in time-entry-state-machine.

The separate time-entry application loads a .NET WebAssembly runtime, forwards Limen messages through a tiny transport, and executes an F# engine behind a single [JSExport] marshalling method. That consumer existed before the site conversion and required no application-specific change to BrowserKernel.

One browser boundary, multiple application engines. The seam is real; superiority is still an open empirical question.

L-3 · a defect that changed the kernel

Real use found a silent binding failure.

Observed once, then converted into a regression check.

The time-entry consumer once put data-if directly on a <p>. Limen only interprets conditional rendering on <template>, so the attribute was silently ignored. The live page exposed the defect when tests did not.

That incident did not justify a defect-rate claim. It justified a product change: misplaced data-if/data-each now surface a binding error and have regression coverage.

Structural evidence

What follows from the current implementation.

Useful, but not presented as measured improvement.

Application decisions are out of the DOM layer

The site's browser-side files contain no release, stale-evidence, reconciliation, or quiz decision vocabulary. Those concepts live in F#.

Effects cross explicitly

The F# engine requests effects as protocol data. Limen performs them and returns classified evidence with correlation IDs.

Unsupported authority is visible

The challenge includes clipboard read and programmatic focus specifically because Limen does not expose them. The correct answer is a protocol change, not a hidden browser call.

Unknown outcomes remain representable

OutcomeUnknown is distinct from failure and is projected as unresolved reconciliation work rather than an automatic retry.

Not measured

Claims this site still refuses to make.

The conversion to F# WebAssembly does not change this list.

“Limen reduces development time.”

Not measured. No controlled construction comparison isolates Limen.

“Limen reduces defects.”

Not measured. Existing defects and fixes are observations, not a comparative rate.

“Limen saves tokens or context.”

Not measured. The relevant agent telemetry has not been available consistently enough to support this claim.

“F# WASM is faster than TypeScript.”

Not measured. This work establishes an architectural boundary, not a runtime-performance result.

“Agents understand Limen better.”

Not measured. Documentation usability and architecture checks are not an agent-accuracy experiment.

“This produces better UIs.”

Not measured. Visual quality requires its own evaluation; Limen governs authority and mechanics, not taste.

Adjacent evidence

Ordo/SDE results are still not Limen results.

The distinction remains important even when the architectures complement each other.

Echelon Foundry's engineering experiments include useful results about heterogeneous verification, explicit state, and construction method. Those experiments did not isolate Limen. The strongest direct result in that corpus remains the fresh-agent verification pass that found five findings with zero overlap with the builder's own 90-test suite, four of them real defects. That supports heterogeneous verification on that run; it does not support a Limen effectiveness percentage.

The experiment worth running

Compare the boundary, not the marketing.

A useful next Limen experiment would hold requirements, model, effort, and verification constant while changing the browser architecture. Preregister the predictions and let an independent pass inspect both.

  1. 01
    Same requirement set and starting constraints.
  2. 02
    Limen/F# WASM arm versus a conventional browser-state architecture.
  3. 03
    Measure time, files inspected/changed, build cycles, rework, defects by discovery stage, and escapes.
  4. 04
    Record model identity and token/cost data only when actually exposed.
  5. 05
    Freeze predictions before either arm begins.
  6. 06
    Run heterogeneous verification on both.
