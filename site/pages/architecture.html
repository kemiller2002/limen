Architecture · self-hosting implementation

The application is WebAssembly. The browser boundary is Limen.

This site uses an F#/.NET WebAssembly reference engine.

The site uses the architecture it describes. Static HTML and CSS remain browser-native. Limen owns DOM bindings and browser effects. A tiny transport loads a .NET WebAssembly runtime. All application state, transitions, capabilities, obligations, effect interpretation, and view projection live in the engine — on this site, written in F#. Limen does not require F#: the engine role is defined by the boundary, not by a language.

Runtime path

Four layers. One authority boundary.

Every arrow crosses plain serializable data or browser-native structure.

HTML + CSS

Semantics, labels, layout, focusable controls, responsive presentation.

site/pages/*.html
Limen BrowserKernel

Turns interactions into semantic events, applies projections, executes effects.

src/kernel/
WASM transport

Loads .NET and forwards one JSON message in, one JSON result out.

site/app/wasm-engine-transport.ts
WASM application engine

Owns meaning: state, legal transitions, evidence, authority, obligations, capabilities, projection. F#/.NET on this site.

site/fsharp/Limen.Site.Engine/

The only C# in the site application is the tiny [JSExport] marshalling shim required by .NET's source-generated JavaScript export mechanism. It contains no application state or decision: it forwards the serialized message directly to Limen.Site.Engine.Dispatch.handle.

The contract

The boundary carries evidence, never application objects.

Defined by the npm package in src/protocol.ts.

This separation is what lets the application move across a real WebAssembly boundary. The TypeScript package does not need F# types, and this site’s F# engine does not need DOM types. Both sides agree only on the serialized protocol — which is why any WASM language that can read and write it can take the engine role.

Language-neutral contract

One contract. Each guest enforces it in its own compiler.

No guest language is canonical. F# is the reference implementation, not a protocol requirement.

The hard cases

Why this is more than state management.

These are the cases the site now runs through F#.

Capability

Approval is not a button state

Tests and security evidence must both pass before F# projects approval capability. The DOM receives the result; it does not derive it.

Staleness

Older evidence cannot win a race

The F# engine carries the latest request identity. A late result for an older request is observable and discarded rather than silently overwriting current state.

Unknown effect

Timeout is not failure

After dispatch, a timeout becomes reconciliation-required state. No retry capability exists until authoritative evidence resolves what happened.

Missing capability

No browser escape hatch

If focus control or clipboard read is not in the protocol, application code cannot quietly reach for a DOM/global API. It becomes an explicit protocol decision.

Compute in code

Closed types make the legal state space visible.

This site’s release demo, written in F#, is not built from four independent flags. Deployment can be not started, in flight, deployed, failed, or reconciliation required. The transition function controls which moves exist.

  1. 01
    Evidence changes are legal only before approval.
  2. 02
    Approval exists only after both required evidence gates pass.
  3. 03
    Deployment exists only after approval.
  4. 04
    Only the matching correlation may complete an in-flight effect.
  5. 05
    OutcomeUnknown creates reconciliation, not retry.
