Architecture

What runs where, and why.

Limen is roughly eighty lines of contract and one bridge file. The interesting part is not the code — it is where the line is drawn, and what becomes impossible once it is.

The contract

Two message shapes cross. Nothing else.

Defined in src/protocol.ts.

Three properties carry all the weight. It is data, not calls — no callbacks, no DOM nodes, no object identity, so every value survives a round trip through JSON. It is generic — the kernel's types mention no domain concept, so there is nowhere for a feature to add a special case. And it is total — every response carries a complete view, so the kernel never diffs or patches; the engine says what things are now.

Note what SemanticEvent does not carry: no element id, no DOM node, no event object. An engine that knew about element ids would be coupled to markup, and changing the HTML would become a change to application logic.

State ownership

Four kinds of state. One owner each.

“Owns” means: if two disagree, this one is right.

Who owns what, and what that rules out
KindExamplesOwnerConsequence
ApplicationWhich screen is showing; what is in the draft; is a save in flightEngineAnything the application would behave differently because of lives here — including things that feel like “UI state”
DOMtextContent, disabled, which templates are mountedThe DOM, written by the kernelOutput only. Never read back as truth
Browser-localFocus, scroll, caret, hover, animation progressThe browserDeliberately untracked. CSS and native behavior handle it
ExternalServer records, localStorage contentsThe external systemThe engine never holds this — only evidence about it, with a classified outcome

That last row is subtle and load-bearing. When the server says a customer exists, the engine does not learn that a customer exists. It learns that it received a response, at a moment, with a classified outcome, that said so. That distinction is what makes OutcomeUnknown representable at all.

There is exactly one place the kernel reads from an element: readValue(), which lifts .value off a form control into a SemanticEvent. That is transporting a keystroke, not reading state — from that moment the engine's copy is authoritative. There is no querySelector anywhere in the engine, and there cannot be.

Reasoning

Why the line sits here.

The part to reason from when the docs do not cover your case.

Why must the engine own all application state?

State in two places will disagree, and when it does, nothing tells you which is right. Bugs of that kind are not fixed by being careful — they are fixed by making the second copy impossible. One owner also means one place to look, which matters far more for an agent than for a human: a human asks; an agent guesses and continues.

Why must the kernel stay ignorant?

The moment it knows what one event name means, it becomes a place application logic can accumulate. Bridges that “just handle this one case” grow into second application frameworks. Six generic attributes leave no hook to grab.

Why represent effects as data?

It keeps transitions pure and testable with no browser or network; it makes every external interaction visible at the boundary instead of buried in a function; and it forces the failure cases into the type system. You cannot request an HTTP effect without handling what happens when it fails.

Why is OutcomeUnknown separate from failure?

A request that timed out after dispatch may have been processed. The kernel cannot know, and claiming otherwise causes duplicate records. The honest answer is “we don't know” — and the right recovery is domain-specific, which is precisely why the kernel reports instead of deciding.

Why project capabilities instead of deriving them?

“Disable Save when the text is empty” is a business rule. If CSS or the DOM re-derives it, the rule now lives in two places and will drift. Projecting saveDisabled keeps one rule in one file.

Why serializable, when nothing is serialized?

Because the alternative is a redesign later. Today the transport passes objects in process. Because the types admit nothing unserializable, adding a codec — or a WebAssembly engine — is additive rather than structural. One consumer has already done exactly that.

A note on the name

There is no WebAssembly in this package.

The published package is still called @echelon-foundry/typescript-wasm-kernel, and it contains no .wasm file, no loader, and no WebAssembly.instantiate call. The name described the shape of the boundary — narrow, serializable, and therefore drivable from a WebAssembly module — rather than the current implementation.

That shape has since been demonstrated: a separate Echelon Foundry project runs an F# engine behind this exact interface, over the .NET WebAssembly runtime, and needed no change to the kernel to do it.
