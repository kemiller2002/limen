The first two rows look identical at a glance and are not. Both are invalid-response — a real response arrived and would not decode — but the status separates them, which is why the kernel carries it. A 404 or 500 whose error page is HTML is the server refusing; a 200 whose body is malformed is a broken payload. The first can be worth retrying. The second never is.

This distinction was added because building this page exposed its absence: the status was being discarded, leaving the two cases indistinguishable. Note also what the kernel does not do — it never decides that 404 means “not found”. In a lookup that may be routine; in a save it is a bug. Only the engine knows which.

The last row is why OutcomeUnknown exists as its own outcome rather than being folded into failure. A request that timed out after dispatch may have been processed. Calling that a failure is a lie, and it is the lie that produces duplicate orders.

Demo 04

Where does this code go?

The question an agent has to answer correctly every time.

Task 1 of 8

This is the decision Limen is really about. Every task above has exactly one right answer, and the rule that produces it is short enough to state: if the application would behave differently because of it, it belongs in the engine. Appearance is CSS. Structure is HTML. Reaching the outside world is an effect request. Carrying an event across the boundary is the kernel's job, and the only one it has.

What you just used

One kernel. One engine. No framework.

Every demonstration on this page is bound with the same six attributes and served by a single BrowserKernel over one engine. The page itself is static HTML — the prose you are reading is not managed by anything.
