F# WebAssembly demonstrations

Problems that are hard for the right reasons.

These are not counters or todo lists. Every interactive decision below is made by the same F# engine running as WebAssembly behind the real Limen kernel. The browser still owns rendering and I/O. The application owns legality, evidence, authority, and what happens next.

The success and network-failure buttons use real Limen HTTP effects. The timeout-after-dispatch button deliberately injects an already-classified OutcomeUnknown into the F# state machine so this safety case is deterministic on a static GitHub Pages site. Limen's transport-level timeout classification is covered separately by kernel tests. The F# application then removes deploy capability and creates the reconciliation obligation.

Challenge 02

Make stale evidence arrive last.

A race condition without timers, so you can control the order yourself.

In callback-shaped code, response A often wins simply because it runs last. Here the engine knows which correlation is current. Delivering A after B has started records the stale arrival but cannot mutate the accepted policy result. The check is pure F# state transition logic; no DOM timing rule is involved.

What these exercises prove

The boundary survives nontrivial state.

None of the examples requires Limen to learn release vocabulary, policy semantics, retry rules, or quiz answers. The browser side remains generic while the F# application becomes as complicated as the domain requires.
