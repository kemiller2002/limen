F# application authority · Limen browser boundary

Make the browser a mechanism, not a second application.

Limen gives the browser a narrow job: carry semantic events, apply a projection, and perform explicit effects. The application behind this page is F# compiled to WebAssembly. It owns the state, legal transitions, capabilities, obligations, and interpretation of evidence.

Why the boundary exists

Hard UI problems are usually authority problems.

The issue is not whether JavaScript can update a span. It can.

Legality

Can this action happen now?

Release approval depends on evidence. Deployment depends on approval. A disabled button should reflect that decision, not make it.

Evidence

Is this response still current?

Two requests overlap. The older response arrives last. Without correlation and explicit state, stale evidence silently wins.

External effects

Did the write fail, or do we not know?

A timeout after dispatch is not failure. Treating it as failure and retrying blindly is how duplicate effects are created.

Placement

Which layer is allowed to decide?

HTTP is browser mechanism. Interpreting 409 is application meaning. Focus control is not currently a Limen capability. Those distinctions are the architecture.

Self-hosting proof

The site follows the architecture it describes.

HTML and CSS remain browser-native. Limen turns interactions into plain messages and performs browser effects. A tiny transport loads the .NET WebAssembly runtime. Every application decision on the interactive pages lives in the F# engine.

The npm package itself is still a TypeScript browser kernel. The F# WASM site engine is a real consumer of that package boundary, not code shipped as part of the kernel.

  3. 03

  4. 04

The buttons are not the rules. F# projects capabilities such as canApproveRelease and canDeployRelease from authoritative state. Limen only applies them to the DOM. A timeout becomes ReconciliationRequired, which removes deployment capability until new authoritative evidence arrives.

What follows from the boundary

Structural consequences, not benchmark claims.

The evidence page separates what is enforced from what remains unmeasured.

Application state has one owner

The F# engine decides. The DOM is projection output and browser-local state remains browser-local.

Effects are evidence

The browser reports classified outcomes. The engine decides what those outcomes mean to the application.

Capabilities are projected

The UI does not reconstruct permission by peeking at text, CSS classes, or unrelated flags.

The boundary is executable

This site crosses it for real: static HTML → Limen → serialized protocol → F# WebAssembly → projection.
