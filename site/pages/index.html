Browser architecture

The threshold your application stands behind.

Limen is an explicit boundary that keeps browser capabilities separate from application authority. The browser renders and interacts. Your application owns what things mean. Nothing crosses between them except plain, serializable data.

See it run How it works Source

Exactly one place owns application state, and it is not the browser.

  • zero runtime dependencies
  • six HTML attributes
  • ~80-line contract

The problem

Truth gets smeared across three places.

Most browser applications end up here by accretion, not by decision.

Symptom

Three copies, no owner

A JavaScript store, the DOM itself, and the server each hold a version of the same fact. When they disagree, nothing tells you which one is right.

Symptom

Impossible states, representable

isSaving and isComplete and hasError can all be true at once. Nothing prevents it, so every reader must invent a meaning for it.

Symptom

Decisions hidden in handlers

Business rules end up inside click handlers, mixed with DOM updates and network calls, where they cannot be tested without a browser.

Symptom

Agents edit the wrong layer

When any layer could plausibly hold a rule, an AI agent has to guess which one does — and it will guess, silently, then keep going.

The core idea

Five responsibilities, none overlapping.

If a layer could hold a rule, eventually it will. So none of them can.

Who owns what
LayerOwnsNever
HTMLDocument structure, semantics, labels, native validationDecides anything
CSSPresentation, hover, focus, motionEncodes a business rule
BrowserLayout, paint, native input behaviorIs asked for permission
Limen kernelCarrying events in, applying projections out, performing effectsKnows what an event means
EngineState, transitions, validation, capabilities, what to showTouches a browser API

The kernel understands six HTML attributes and no application vocabulary at all. It does not know what checkAvailability means or what a customers list is. It moves opaque strings and plain data across a boundary — which is exactly what stops application logic from accumulating in the browser layer.

What follows from the boundary

Consequences, not claims.

Each of these is true by construction — it follows from where the line is drawn. None of them is a measured result, and this site does not present them as one.

What has and has not been measured →

  1. 01
    One source of truth. State exists only in the engine. The DOM is output, never input.
  2. 02
    Illegal states unrepresentable. State is a union, so “saving and already saved” cannot be written down.
  3. 03
    Deterministic transitions. (state, command) → state is pure, and testable with no browser.
  4. 04
    Honest failure. Every effect reports Success, Failure, Cancelled, or OutcomeUnknown. “We don't know” is a real outcome.
  5. 05
    Portable logic. The engine touches no browser API, so it can move to another language without rewriting behavior.
  6. 06
    Less to audit. Browser access lives in one file, and the build fails if it leaks.

Honest limits

What Limen does not give you.

Recorded, not hidden. Several are deliberate.

No routing or history

Back and forward do not move between screens. Screens work within one page load; URL integration is not implemented.

Two browser capabilities

HTTP and localStorage. No clipboard, files, timers, navigation or IndexedDB — adding one is a deliberate protocol change.

No focus management

Removing a focused list item drops focus. A known gap.

No virtualization

Every projected item becomes a DOM node.

More ceremony when trivial

For a genuinely simple page, a small component framework is less work. Limen earns its keep when behavior is complex.

No WebAssembly here

The boundary is designed for it and one consumer runs an F# engine across it — but this package ships TypeScript.
